# Runbook: secret rotation

Covers routine rotation and the urgent case — a secret that has been disclosed.

**Nothing in this repository has ever held a real secret.** Local development
key material is generated by `scripts/generate-local-secrets.sh` into a
gitignored directory and is not usable anywhere else.

---

## The rule that governs the urgent case

> **Rotate first. Rewriting history does not un-disclose a value that has
> already been on a disk, in a CI log, or in somebody's clone.**

A disclosed credential is compromised from the moment it was disclosed, not from
the moment somebody noticed. The instinct to force-push the commit away first is
the wrong order, and it costs the window in which the credential is still valid.

---

## A secret has been committed

### 1. Rotate, immediately

Before anything else, and before telling anyone it is handled.

| Secret | How |
|---|---|
| RDS master password | Managed by AWS (`manage_master_user_password`). Trigger rotation in Secrets Manager; no password passes through Terraform, its plan output, or state |
| Application database credentials | Not applicable — services use IAM database authentication and hold no password |
| Applicant pepper | **See the special case below. This one is not a normal rotation.** |
| OIDC client secret | Rotate at the identity provider, update the Secrets Manager entry, restart pods to re-read the mounted file |
| Partner API key | Delete the key in API Gateway, issue a new one, notify the partner |
| AWS access key | There should be none: workloads use IRSA and CI uses OIDC. If one exists, delete it and find out why it existed |
| KMS key material | Not rotatable in this sense. If a key is compromised, the data under it is compromised; disable the key and re-encrypt |

### 2. Confirm the new one works and the old one is refused

Both halves. A rotation that leaves the old credential valid is not a rotation.

### 3. Establish whether it was used

CloudTrail for AWS credentials; the identity provider's logs for client secrets;
API Gateway access logs for API keys. **This is the step that decides whether
this is an incident or a near miss**, and it is the one most often skipped
because the panic is over by the time you reach it.

### 4. Only now, consider history

```bash
# Confirm what is actually in the history, and where.
gitleaks detect --source . --config .gitleaks.toml --redact --verbose
```

**History is never rewritten automatically in this repository.** No script and
no agent does it. It requires explicit human approval because it:

- changes every commit hash from the rewrite point onwards;
- invalidates every existing clone — collaborators must re-clone, not pull;
- breaks every external reference to a commit hash (CI runs, tickets, review
  links, deployment records);
- does **not** remove the value from forks, caches, or anything already indexed.

If, after all that, the decision is to rewrite:

```bash
# git-filter-repo, not filter-branch: filter-branch is deprecated, slow, and
# has known correctness problems with tags and refs.
pip install git-filter-repo

# On a FRESH clone. filter-repo refuses to run on a repository with a remote
# already configured, deliberately -- that guard exists to stop an accidental
# push of rewritten history over a shared branch.
git clone --no-local /path/to/repo repo-rewrite
cd repo-rewrite

git filter-repo --path path/to/leaked-file --invert-paths
#   or, to replace a literal value everywhere it appears:
#   git filter-repo --replace-text replacements.txt

# Verify BEFORE pushing.
gitleaks detect --source . --config .gitleaks.toml --redact
```

Then, with everyone told in advance:

```bash
git push --force-with-lease --all
git push --force-with-lease --tags
```

`--force-with-lease`, never bare `--force`: it refuses if the remote has moved
since you last fetched, which is the difference between rewriting history and
destroying somebody else's work.

Afterwards: every collaborator re-clones. A `git pull` onto rewritten history
produces a merge that reintroduces the secret.

### 5. Write it down

Timeline, scope, whether it was used, what changed to stop it recurring. See
[`../../security/incident-response.md`](../../security/incident-response.md).

## The applicant pepper is a special case

`ApplicantReference` is `HMAC-SHA-256(pepper, applicant identity)`. The pepper is
not a credential that can be swapped out — **it is an input to a value stored in
every table and every audit record.**

Rotating it changes every reference. That means:

- existing references no longer match newly computed ones;
- cross-context joins break, because the application, workflow, document and
  audit contexts all key on the reference;
- **the audit trail cannot be recomputed**, by design. Its records are
  append-only and hash-chained. Rewriting them to use new references would break
  every chain hash, which is precisely the property the chain exists to provide.

So a pepper rotation is a **data migration**, not an operational task:

1. Introduce a versioned pepper: store the pepper version alongside each
   reference.
2. Compute new references with the new version; keep resolving old ones with the
   old pepper, which must be retained for as long as any record uses it.
3. Migrate forward gradually, per aggregate.
4. **Never rewrite audit records.** They keep their original references, and the
   version field is what makes them interpretable later.

Rotate the pepper only if it is actually disclosed. If it is, note what the
disclosure means: the pepper alone does not reveal an identity — HMAC is not
reversible — but it allows an attacker who *guesses* an identity to confirm it
by computing the reference. That is a confirmation oracle, not a decryption, and
it matters most for a small or enumerable population.

## Routine rotation

| Secret | Interval | Mechanism |
|---|---|---|
| RDS master password | 30 days | Automatic, Secrets Manager |
| OIDC client secret | 90 days | Manual, at the IdP |
| Partner API keys | 180 days, or on partner request | Manual |
| Applicant pepper | **Never on a schedule** | See above |
| KMS keys | Annual | Automatic (`enable_key_rotation`); AWS retains old material, so existing ciphertext stays readable |
| Local development keys | Whenever | `make local-secrets` |

Rotation is only real if the application picks it up. Secrets arrive as **files**
via the Secrets Store CSI driver, so a rotated secret requires either the
driver's rotation-reconciler or a pod restart. A rotation nobody restarted is a
rotation that has not happened yet.

## Verifying nothing is committed

```bash
make secret-scan          # working tree and full history
```

or the hook, which is where you want to catch it:

```bash
pip install pre-commit
pre-commit install
```

A secret caught by the hook is a typo. A secret caught by CI is already in the
branch's history. The gap between those is a few seconds.
